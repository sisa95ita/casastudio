# AI-D1 — First provider failure: offline diagnosis and fix

The deepest demonstrated request defect was **unsupported `oneOf` unions in the strict Structured Outputs schema**. The production adapter used Zod's raw JSON Schema exporter plus a custom required/nullability pass. That pass left two `oneOf` nodes unchanged: the Furniture result union and the Furniture operation union. OpenAI's installed SDK explicitly rewrites Zod discriminated `oneOf` unions to supported `anyOf` unions. AI-D1 bypassed that compatibility step.

The historical OpenAI HTTP status, provider code/message, error class and request ID are **unavailable**. The owner confirmed that only the CasaStudio wrapper was captured; the local API container log also had no record of the attempt. No additional live call was made to recover them. A schema rejection is consistent with the emitted invalid schema and rapid failure, but the historical HTTP response cannot be asserted as fact.

2. `ProposeFurnitureEditService.propose` — `apps/api/src/ai/application/propose-furniture-edit.service.ts`: strict request parsing, `AuthorizedProjectLoader.load`, persisted revision and canonical context.

5. `OpenAIFurnitureEditProvider.interpretFurnitureEdit` — `apps/api/src/ai/openai/openai-furniture-edit.provider.ts`: build request, await SDK boundary, decode text JSON, parse provider output.
6. The SDK wrapper calls `client.responses.create(...)`. SDK 7.23.0 posts the body to `/responses`; `create` does not convert a manually supplied JSON schema.
7. `validateFurnitureEditResult` — `packages/ai/src/furniture-edit.ts`: source/selection/Room/catalog authority and detached deterministic command validation. This remains mandatory.
8. Former error translation: `normalizeOpenAIError` in the image adapter → `toApiProblem` in `generate-design-proposal.service.ts` → `ProblemDetailsFilter`. Shared normalization and Problem mapping now live in independent modules, with compatibility re-exports for existing callers.

The original public detail, exactly “The AI provider could not generate the design.”, comes from the fallback in `normalizeOpenAIError`, invoked by the adapter's SDK-request catch. The original post-response parsing catch used a different detail and `AI_INVALID_PROVIDER_RESPONSE`. Thus the captured error locates the historical failure at the SDK request boundary, rather than successful-response decoding or CasaStudio command validation. It does not distinguish a locally thrown SDK error from a provider HTTP rejection.

## 2. Demonstrated schema defect

The exact original production adapter was invoked offline with the existing synthetic Furniture fixture and a mocked SDK boundary. It constructed the request successfully, with these schema paths:

```text
schema.properties.result.oneOf
schema.properties.result.oneOf[0].properties.operations.items.oneOf
```

The original schema had 2 `oneOf` nodes, 1 nullable `anyOf`, and 11 object schemas. Its root was an object; all objects had `additionalProperties:false`; the custom pass made all properties required; optional Transfer rotation was represented as nullable. Those aspects were already correct. Operation count was already bounded to 1–8. The defect was the unsupported discriminated-union representation, not the provider-neutral domain contract.

Official OpenAI documentation supports nested `anyOf`, requires an object root and all fields to be required, and allows required nullable fields. See [Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=responses). The installed SDK provides direct corroboration in `apps/api/node_modules/openai/src/helpers/zod.ts`: `zodV4ToJsonSchema` explicitly replaces discriminated `oneOf` with `anyOf`, because discriminator literals make the branches mutually exclusive.

There is no `response_format` Chat Completions parameter, no image input, no `image_generation` tool, no `action`, no size/quality/format image settings, no tool choice or parallel-tool setting, no continuation, and no fallback. There are no tools to parallelize. Retry and timeout are client configuration, not request-body fields: `maxRetries:0`, `timeout:60000`.

The corrected SDK helper emits draft-7, 0 `oneOf` nodes, 3 nested `anyOf` nodes (result, operations, nullable rotation), and the same 11 strict objects. Both the object passed to the SDK seam and the serialized body from the actual installed SDK are inspected in regression tests. The transport is a fake `fetch` returning synthetic responses; it makes no network call.

## 4. Model and capability

The repository `.env` and configuration default specify `OPENAI_REASONING_MODEL=gpt-5.6-sol`. That model is passed unchanged to the Furniture provider. Official [GPT-5.6 Sol documentation](https://developers.openai.com/api/docs/models/gpt-5.6-sol) lists Responses and Structured Outputs support. There is no demonstrated model/capability mismatch, so the model was not changed. Account-specific access cannot be verified from the missing historical exception and was not probed with a live request.

## 5. Error loss and image terminology

`normalizeOpenAIError` retained the raw SDK error as `DesignGenerationError.cause`, but mapped otherwise-unclassified failures (including a possible HTTP 400) to generic `generation_failed`. It supplied image-design wording. `toApiProblem` then created a new `ApiProblemError` without the cause. The generic exception filter could log only that new wrapper; the service had no sanitized provider-diagnostic log. This explains the missing upstream metadata.

Image behavior did not leak into request construction or decoding. The reuse was limited to a generic Responses-client type and error infrastructure whose fallback/timeout messages used image terminology. Those messages are now operation-aware; existing image callers retain their prior default behavior.

## 6. Fix and diagnostics

- Added `buildOpenAIFurnitureEditRequest` and a wire-only envelope using the existing result/command schemas. Official `zodTextFormat` replaces the handwritten schema conversion.
- Transfer's optional canonical rotation is required/nullable only on the wire. `null` still becomes omission before canonical parsing. No canonical schema, identifier, numeric, batch, catalog, placement or architecture validation was weakened.
- Added failure stages: `request_construction`, `provider_request`, `response_decoding`, `provider_result_validation`. The service additionally identifies `context_validation` and `command_validation`.
- Added content-free diagnostics: allowlisted SDK error class, bounded HTTP status, sanitized provider code/type/parameter, validated provider request ID, a known unsupported-schema keyword where identifiable, and a safe message constructed locally. Raw upstream messages are never logged, because they can quote keys or user input. Headers, bodies, instruction text, canonical context and raw SDK error/cause are not passed to the logger.
- The service emits structured diagnostics before converting to a public Problem. Existing Pino HTTP correlation remains in use. Successful-response parsing failures retain `_request_id` where supplied by the SDK.
- Shared `openai-error.ts` retains existing classification/retry-after behavior. Shared `ai-problem.mapper.ts` preserves public status/code abstraction and adds Furniture-specific titles/details. Generic image wording is removed from AI-D1. Raw causes are intentionally not forwarded to the generic exception logger.
