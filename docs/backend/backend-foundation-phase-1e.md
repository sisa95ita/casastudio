# Backend Foundation Phase 1E

## Purpose

Phase 1E completes the backend foundation with reproducible Jenkins CI and
focused repository hardening. It does not add Connected App behavior, frontend
authentication, frontend API calls, Project mutations, deployment, registry
publishing, production infrastructure, or broad source-code refactoring.

## Jenkins Architecture

Jenkins is isolated from the CasaStudio runtime. The runtime remains:

```text
web
API
PostgreSQL
Keycloak
```

Local CI is a separate stack:

```text
compose.jenkins.yml
        ↓
Jenkins controller image
        ↓
one inbound build agent
        ↓
Pipeline as Code from Jenkinsfile
```

`compose.jenkins.yml` is managed independently:

```bash
pnpm jenkins:up
pnpm jenkins:down
pnpm jenkins:logs
pnpm jenkins:config
```

Jenkins is not added to `compose.yml`, `compose.dev.yml`, or
`compose.test.yml` because it is development infrastructure, not an application
dependency.

## Controller And Agent Separation

The controller image is built from `infra/jenkins/Dockerfile` on the Jenkins LTS
JDK 21 image. It installs only the direct plugins declared in
`infra/jenkins/plugins.txt` and loads JCasC from
`infra/jenkins/casc/jenkins.yaml`.

JCasC sets:

- controller executors to `0`;
- anonymous access disabled;
- local security realm with the administrator supplied from environment
  variables;
- a permanent `casastudio-agent-node` node;
- agent executors to `1`;
- a local CasaStudio system message.

CSRF protection is preserved by leaving Jenkins' default crumb issuer enabled.

The agent image is built from `infra/jenkins/agent.Dockerfile`. It provides
Git, Node.js 24, Corepack, Docker CLI, Docker Compose support, and native system
libraries required by the repository. The pipeline activates the exact
repository package-manager version: `pnpm@11.10.0`.

The Jenkinsfile also uses:

```groovy
disableConcurrentBuilds()
```

This keeps local Colima/Docker resources predictable and avoids overlapping
image builds for the same job.

## Docker Access

Only the build agent mounts `/var/run/docker.sock`. The controller never mounts
the Docker socket.

At container startup, the agent entrypoint reads the mounted socket's numeric
group ID, creates a matching group inside the container when necessary, adds the
`jenkins` user to that group, and then starts the inbound agent process as the
non-root `jenkins` user. This avoids hard-coding a host-specific Docker socket
GID while keeping normal build execution non-root.

This gives the agent control of the local Docker daemon. It can build images,
start containers, and remove CI-tagged images or CI Compose services. This is a
trusted local-development design, not a sandbox and not a multi-tenant security
boundary. A hosted Jenkins migration should use isolated ephemeral agents or a
remote container builder.

## JCasC And Secrets

JCasC stores non-secret defaults in source. Actual values stay outside Git:

- `CASC_JENKINS_ADMIN_ID`
- `CASC_JENKINS_ADMIN_PASSWORD`
- `CASC_JENKINS_ADMIN_EMAIL`
- `CASC_JENKINS_AGENT_SECRET`
- future GitHub credentials, webhook secrets, and registry credentials

The initial administrator is created from local environment variables. The
inbound agent secret is generated by Jenkins for the JCasC-created node; copy it
to the ignored `.env` as `CASC_JENKINS_AGENT_SECRET` before expecting the agent
to connect.

## Pipeline Stages

The Declarative Pipeline is designed for a Jenkins Multibranch Pipeline and
uses the SCM revision Jenkins checked out. It does not hardcode one branch.

Stages are sequential:

1. Checkout
2. Toolchain Verification
3. Install Dependencies
4. Repository Validation
5. Schema
6. Geometry
7. Web
8. API Static Validation
9. API Database Integration
10. Compose Validation
11. Docker Image Build

The same full sequential policy currently applies to feature branches, pull
requests, and `main`. No image push or deployment occurs on any branch.

## Dependency And Cache Policy

CasaStudio's current Jenkins installation is local development CI running on a
Docker/Colima-backed Mac, so repository validation favors predictable resource
usage over maximum throughput.

CI runs:

```bash
pnpm install --frozen-lockfile
```

The pipeline activates `pnpm@11.10.0` through Corepack and checks that
`pnpm-lock.yaml` was not modified. It does not cache `node_modules`. Jenkins sets
`TURBO_CONCURRENCY=1` to serialize Turbo task execution on the local Docker
host. This is a CI execution policy, not a monorepo limitation; normal
developer `pnpm lint`, `pnpm test`, and `pnpm build` commands keep their default
Turbo behavior. The value can be revisited when Jenkins moves to more capable
infrastructure.

## Validation Details

Repository validation runs:

```bash
pnpm lint
pnpm test
pnpm build
```

Turbo is configured so `test` tasks depend on dependency package `build` tasks.
Workspace packages export their built `dist` entry points, so a clean checkout
must build dependency packages such as `@casastudio/schema` before tests in
dependents such as `@casastudio/geometry`, `@casastudio/api`, and
`@casastudio/web` resolve those package exports.

Schema validation also runs schema lint, tests, build, JSON Schema generation,
and a Git diff check for `packages/schema/json-schema/project.schema.json`.

Geometry validation runs the geometry package lint, tests, and build to keep
the Node ESM import-specifier behavior exercised.

Web validation runs:

```bash
pnpm web:lint
pnpm web:test
pnpm web:build
```

The Vite chunk warning remains informational. No frontend authentication,
protected routes, token storage, landing page, or API consumption is added.

API static validation runs:

```bash
pnpm api:lint
pnpm api:test
pnpm api:build
pnpm db:validate
pnpm db:generate
```

No Prisma schema change or migration is introduced.

## PostgreSQL-Backed Tests

Database-backed API tests are exercised with a disposable PostgreSQL service
from `compose.yml` plus `compose.test.yml`.

The pipeline:

- creates a unique Compose project name from the Jenkins build number;
- assigns an overridable test PostgreSQL host port through
  `CASASTUDIO_TEST_POSTGRES_PORT`;
- starts only the PostgreSQL test dependency;
- waits for `pg_isready`;
- sets a CI `DATABASE_URL`;
- applies migrations with `pnpm db:migrate:deploy`;
- runs API tests with `DATABASE_URL` present so persistence tests do not skip;
- always tears down services and volumes.

Keycloak is not required for the current automated database-backed tests because
HTTP tests use deterministic JWT fixtures.

## Reports And Coverage

Package-level Vitest runs emit JUnit XML under `test-results/`, and Jenkins
publishes them with the JUnit plugin. Generated reports and coverage directories
are ignored by Git.

Coverage thresholds are not introduced in Phase 1E. Coverage generation can be
standardized after a stable baseline is available.

## Compose And Image Builds

CI validates:

```bash
docker compose config --quiet
docker compose -f compose.yml -f compose.dev.yml config --quiet
docker compose -f compose.yml -f compose.test.yml config --quiet
docker compose -f compose.jenkins.yml config --quiet
```

After validation succeeds, CI builds the application images sequentially:

```text
casastudio-web:ci-<build-number>
casastudio-api:ci-<build-number>
```

Images are not pushed. Deployments are not performed. CI-tagged images are
removed in post actions.

Post-build cleanup is best-effort and scoped to the CI Compose project plus
CI-tagged application images. Cleanup reports Docker failures in the build log
but exits successfully from the post action so it does not hide an earlier
pipeline failure or fail a successful build only because a CI object was never
created.

## GitHub Flow

CasaStudio uses lightweight GitHub Flow:

```text
main
  protected integration branch

feature/*
  short-lived work branches

pull request
  review and Jenkins status gate

merge
  only after Jenkins succeeds
```

There is no `develop`, `release/*`, or `hotfix/*` branch model.

Concise branch examples:

- `feature/backend-phase-1e`
- `feature/connected-app-auth`
- `feature/landing-page`
- `feature/project-api-integration`

Because the project currently has one developer, self-review is acceptable.
Pull requests still provide an isolated diff, auditable integration point,
Jenkins status checks, future AI or human review integration, and separation
between work in progress and integrated code.

## GitHub Main Protection

Configure a GitHub ruleset or branch protection rule for `main`:

- require pull requests;
- require the Jenkins status check;
- disable force pushes;
- disable branch deletion;
- require conversation resolution where applicable;
- consider linear history optional;
- evaluate "branch must be up to date" carefully because it can add friction to
  a one-maintainer project.

Do not require an external approval that blocks the sole maintainer. Do not
store GitHub tokens or webhook secrets in the repository.

## Multibranch Setup

Create a Jenkins Multibranch Pipeline for the GitHub repository. Enable branch
and pull-request discovery and point Jenkins at the `Jenkinsfile` from each
revision. Add GitHub credentials in Jenkins Credentials, then configure either a
GitHub webhook or periodic branch indexing.

## Security And Configuration Hardening

Phase 1E adds ignores for local Jenkins state and generated test reports,
excludes Jenkins infrastructure from application Docker build contexts, uses
placeholder-only environment examples, keeps `.env` files ignored, and avoids
committing Postman tokens, Jenkins credentials, Docker registry credentials, or
Keycloak secrets.

Postman artifacts remain safe local-development helpers. The Keycloak realm
continues to use environment placeholders for client and demo-user secrets.

## Preserved Runtime Behavior

Phase 1E does not change API runtime behavior. These routes remain in scope for
preservation only:

- `GET /api/v1/health/live`
- `GET /api/v1/health/ready`
- `GET /api/v1/projects/:id`
- `GET /api/v1/projects/:id/geometry`

JWT issuer/audience validation, owner authorization, administrator override,
DTOs, Problem Details, Swagger development behavior, PostgreSQL persistence,
Keycloak realm behavior, and Postman Authorization Code with PKCE remain
unchanged.

## Troubleshooting

- Missing Jenkins admin variables: `pnpm jenkins:config` fails before startup.
- Agent does not connect: replace the placeholder
  `CASC_JENKINS_AGENT_SECRET` with the generated node secret from Jenkins.
- Docker permission denied on the agent: rebuild and restart the agent so the
  entrypoint can remap the `jenkins` user's supplementary group to the mounted
  socket's numeric group ID.
- Local image builds are killed: reduce Docker/Colima pressure and rerun; the
  pipeline is intentionally single-agent and sequential.
- Database tests skip locally: ensure `DATABASE_URL` is present when running API
  tests outside Jenkins.

## Known Limitations

- Jenkins is local development infrastructure.
- The build agent is static and Compose-managed.
- The Docker socket trust model is local-only.
- No registry push or deployment exists.
- No dependency audit gate is introduced yet.
- Coverage thresholds are deferred until a baseline exists.

## Deferred Work

Connected App work is deferred: frontend authentication, protected routes,
token/session handling, API client generation, Project API integration, Geometry
API integration, and replacing local viewer fixtures.

The broad TSDoc cleanup is also deferred. Existing stale symbol comments that
reference phase numbers, Markdown documents, or implementation history should be
handled in a separate focused refactor.
